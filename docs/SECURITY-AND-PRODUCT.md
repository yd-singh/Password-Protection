# Security and product specification (preview)

## Goal and non-goals
An offline password vault with no registration, backend, autofill, accessibility service, browser or advertising. Core security and manual data recovery are never paid features. Native Android first; shared domain code for future iOS. Pro test entitlement requires an explicit tap, no money; release builds do not expose the test entitlement. Planned Pro: automatic encrypted snapshots, history and verified recovery readiness.

## Threat model
Protect data at rest against filesystem extraction, stolen locked phones and unauthorized backup access. Protect UI on a locked/standard OS with screen restrictions and session timeout. An attacker with recovery key AND backup can decrypt backup independently of device/passphrase (intentional recovery path). An attacker with device credential plus local vault may unlock standard mode. Maximum requires device auth plus independent passphrase. The preview does not defend against root, compromised OS, instrumentation of an unlocked process, malicious keyboards/accessibility, forced unlock, or rollback/deletion of encrypted files. No guarantee of zeroing every plaintext copy. Cloud provider metadata and denial of service are outside encryption confidentiality.

## Keys and format
Random 32-byte local vault DEK generated via SecureRandom. Device AES wrapping key in Android Keystore (time-bounded biometric strong/device credential authorization, 10s; verify hardware security level and per-use alternatives in device tests). Maximum mode: Argon2id with fixed v1 parameters (64 MiB, 3 iterations, parallelism 1, 16-byte random salt), passphrase wrapping via AES-256-GCM inside the device wrapper. Standard mode: device wrapper directly protects DEK. Mode changes and passphrase rotation (`rekey`) re-wrap a fresh DEK and re-seal any wrapped backup key after authentication. AES-GCM 12-byte random nonce, 128-bit tag, distinct versioned AAD labels for each operation. While unlocked, `SessionVault` seals each entry under an ephemeral 32-byte session key so only redacted metadata resides in UI lists and single entries are unsealed on demand. Local header metadata and mode are authenticated by wrapper or cipher. Local file contains no plaintext credentials. Use AtomicFile; no plaintext temporary files. Do not overwrite data when authentication fails. Treat key invalidation as a recovery scenario (`KeyInvalidatedException` -> verified backup reset). Size-bound untrusted backup reads; parse only authenticated plaintext.

Portable backup v1: ASCII PPBACKUP1 then 12 bytes nonce, ciphertext and 16-byte tag; AAD UTF-8 `PasswordProtection/portable-backup/v1`. Payload UTF-8 JSON schema in common `VaultCodec` (`Vault.kt`) / `Codec.kt`, version 1. Backup recovery key is random independent 32-byte value, encoded either as canonical unpadded base64url or a 33-word mnemonic recovery kit (`RecoveryKit` with 8-bit checksum). Each manual backup generates its own key; no need for password KDF on random 256-bit secret. No device key exported. User must independently keep both. Restore into new empty local vault re-encrypts under new local DEK (resetting an existing vault requires backup decryption verification first plus device authentication). Local Pro automatic snapshots generate an independent persistent 32-byte backup key wrapped under the vault DEK (`PasswordProtection/local-vault/v1/backup-key`), perform verified readback on each snapshot write, and retain the 5 newest snapshots; cloud Drive sync will build on this independent backup key lifecycle in a separate network-enabled variant without reusing the local DEK.

## Release gates
1. Reproducible dependency resolution (lock and audit versions), Android debug build and emulator/physical Android 11+ tests; verify no network permission in merged manifest. Test Keystore generation, biometric/PIN fallback, enroll/remove biometric or lockscreen, reboot, background while prompt is open, orientation and power loss. Test downgrade/upgrade and recovery from key invalidation. Ensure authentication callbacks cannot reopen a backgrounded vault.
2. Validate Argon2id known vectors and benchmark parameters on low-end devices. Audit all nonce/key lifecycles, authenticated format, memory handling, UI/IME/clipboard behavior, atomic writes and malformed import size/field constraints. Add automated instrumentation. Do not represent this preview as audited.
3. Pro safety net: implement minimal-scope Drive OAuth (`drive.appdata`), encrypted snapshots only, restore flow, multiple versions, backup age and verified readback. Distinguish “upload succeeded” from “restore tested.” Basic manual backup/recovery remains free. No billing until validation; do not make data access contingent on subscription.
4. Independent security review and remediation before public distribution or storing real credentials.
